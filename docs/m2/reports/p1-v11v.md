## MEDIUM

- **M1. When to retry a refused multi-key settings op is unclear.**
  - **Where:** l. 123 (an op may set several keys), l. 130 (any stale key refuses the whole op), l. 136 ("its
    confirmed `appSeq` for that key has passed the refused base"). The `error` names no key.
  - **Scenario:** an op sets `grid` (base 10, current) and `snap` (base 12; the room has 15). It is refused.
    - Read as "every key passed": `grid` never moves, so the retry never fires, and the app's change is stuck
      without bound.
    - Read as "that one key", the client can't tell which key was stale.
  - **Fix:** "retries once its confirmed `appSeq` of **any** key in the op differs from that key's refused base",
    which is what the room's check implies. Optionally name the stale keys in the `error`.
  - **Not modelled:** the model has one key.
- **M2. The 8-connection cap depends on when the gateway notices a dead socket, which is unstated.**
  - **Where:** l. 189–193 ("counts until the gateway sees its socket close").
  - **Scenario:** one tab on a flapping network (Wi-Fi to cellular, a laptop sleeping) is enough. Each reconnect
    can leave a half-open socket that the gateway still counts until TCP or WebSocket liveness notices it, and the
    spec names no ping or idle timeout. After 8 such reconnects every hello gets `limit` with backoff up to 30 s,
    for as long as the OS keeps the dead sockets open (TCP keepalive defaults run to hours).
  - **Fix:** name a gateway liveness rule (for example, a WebSocket ping every 10 s, and close after 30 s of
    silence), so a dead connection stops counting within a bounded time.

- **M3. Rule 12 contradicts § Room identity on epoch checks.**
  - **Where:** rule 12 (l. 295–296) closes on any welcome whose epoch is below one seen in a writer's welcome.
    § Room identity (l. 396–399) applies epoch checks only to room-built welcomes.
  - **Scenario:** a client that was a writer (it saw 7) has its role lowered to viewer and reconnects. The
    gateway's latest known epoch is 6 (the heartbeat lags). Rule 12 says close; § Room identity says record only.
    Under rule 12 it would loop until the heartbeat catches up.
  - **Fix:** rule 12 should say "a writer's `welcome` names … an epoch lower than …".
- **M4. The settings base after `stale` (op-id) for an op in flight is unstated.**
  - **Where:** l. 138–141 covers an ack (base = the settled `seq`) and a refusal (held changes dropped). `stale` is
    neither: the op may or may not have landed, and the client then resyncs. The code job would have to guess what
    happens to the held changes.
  - **Fix:** one clause saying that after `stale` the held changes wait for the resync, then go out on the
    confirmed `appSeq`. The model did this and found no problem.

## LOW

- **L1. A lost `stale-setting` (or one that became `unavailable`) costs a full resync.**
  - **Where:** l. 134–137, 323–326 ("the rebuilt room decides again"), § Op ids l. 423.
  - **Scenario:** client sends settings op k, which is refused; then op k+1 is accepted. The refusal for k is lost,
    or it was held and its append failed, so it became `unavailable`. The client resends k, which is now ≤ `high`
    and not in `recent`, so the room answers `stale`. The client drops k and resyncs with `since: 0`.
  - **Measured in the model:** all 97 below-`high` `stale` answers were this case. The rebuilt room doesn't "decide
    again" when a later op of the same client landed: it answers `stale`.
  - **Impact:** safe, because resync shows the truth. But it costs the full resync the soft refusal was meant to
    avoid, and the failed-append path is common. `records` refusals have had the same cost since v1.
  - **Fix:** either state it as a cost (rule 5 and § Recovery), or let the room keep refused counters in `recent`
    (for example `[counter, refused-code]`) so a resend gets the same refusal.
- **L2. Seeding decides against the importer's confirmed copy, which may lag the room** (codex lead; MEDIUM
  refuted, kept as LOW).
  - **Where:** l. 98–100.
  - **Scenario:** element X is absent from the importer's confirmed copy. Another writer creates X in the room
    before the import arrives. The importer renumbers its copy at version 1,500 to version 1, and the nonce
    tie-break may pick it over the other writer's version 1.
  - **Why only LOW:**
    - Excalidraw ids are random per element, so a concurrent creation of the same id comes only from another copy
      of the same file (two panes may hold different versions of it).
    - New ops wait for catch-up to `welcome.seq` (rule 2), so the window is the time between welcome and send.
    - v1, which renumbered every element, had the same race, so this is not a regression. This is the main
      reason it isn't MEDIUM.
  - **Fix (optional):** one sentence saying the decision uses the confirmed copy after catch-up, and naming the
    race.
- **L3. Epoch numbers incarnations but doesn't fence them.**
  - **Where:** l. 385–388, 399, 406–407.
  - **Scenario (phase 4):**
    - Host A's lease expires, but A hasn't noticed yet. Host B takes the lease, getting epoch 6 (A had 5).
    - B has no writers yet, so it appends nothing. A's appends still succeed, because the fence checks only
      `expectSeq`.
    - A writer welcomed by B (epoch 6) that reconnects and is routed to A sees epoch 5 and treats A as stale
      ("lower than seen"). It loops with backoff until A's next append conflicts or its lease renewal fails.
  - **Impact:** liveness only, bounded by the lease time. The spec already says the epoch is information and the
    fence is the append.
  - **Fix (cheap, same row):** make `append` also check that the lease record's epoch equals the room's
    (`append(…, expectSeq, epoch)`), so a lower epoch really is fenced. Or say in § Room identity that "lower than
    seen" can last until the stale host's lease lapses.
- **L4. Epoch 0 in a viewer's welcome.**
  - **Where:** `epoch(tenant, board) → epoch | 0` (l. 622) returns 0 for a board whose room was never built.
    Viewers never start a room, so a viewer of such a board gets `room.epoch: 0`. But l. 382 says the epoch is "a
    positive integer".
  - **Fix:** allow 0 in a gateway-built welcome ("no room built yet"), or say the gateway omits `room.epoch` in that
    case.
- **L5. The change table's seeding row is inaccurate** (codex lead, confirmed).
  - **Where:** l. 21 says "everything else is sent unchanged", but l. 102–103 holds back an element the room has
    at more than 1,000 below the file's version.
  - **Fix:** add "an element more than 1,000 above the room's copy is held back with a warning".

### R2-M1 (MEDIUM, new). "Differs" lets a refused settings op retry before the client has seen the conflict

- **Where:** l. 139–140: "retries only once its confirmed `appSeq` of **any** key in the refused op **differs**
  from that key's refused base".
- **Scenario:**
  - The client's settings op S1 is acked at `seq` 20. Its entry hasn't arrived yet, so the client's confirmed
    `appSeq` for the key is still 10.
  - A held change goes out with base = max(10, 20) = 20 (l. 144–145).
  - Another writer set the key at 22, so the room refuses the change `stale-setting` (base 20).
  - Confirmed 10 already differs from 20, so the client retries at once, on the same base 20. The room refuses it
    again. The client keeps retrying until it applies entries 20 and 22.
  - This spins, which is the case the same sentence says can't happen ("so a retry can't spin against an entry it
    hasn't applied yet").
- **Measured** (`cas-differs.js` in this session's scratchpad: the round-1 model with "differs" in place of
  "passed", 150 seeds × 4,000 steps):
  - 82 retries fired while the confirmed `appSeq` was still below the refused base; 31 came straight after
    another such retry.
  - Each of these is certain to be refused, because the room's `appSeq` is above the base.
  - Safety held: 0 stuck, 0 `stale-setting` for a logged op. The loop is bounded by entry delivery and the pacer,
    so it wastes ops, but nothing is lost.
- **Fix:** "**is greater than** that key's refused base". The room's `appSeq` is never below a base an honest
  client sends, so a refusal means some key's room `appSeq` > base, and ">" is exactly that.

**For the manager:** PASS. One word to change at l. 140 ("differs from" → "is greater than"). It can ride along
with the v1.1 code job; it needs no re-verify beyond a glance.
